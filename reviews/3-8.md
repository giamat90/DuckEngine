# Review 3-8: `dtex` v0 format, `assets` reader, `tools_assetc` converter

Task: 3-8. Class 2 (new public API in layer 2 `assets`, a new layer 4 tool crate; no protected path touched). Loops: 1 of 3. Open blocker/major: 0.

Delivers: crate `engine/assets` (module `dtex`: header constants, `Texture::parse` validating reader returning borrowed mip views, `encoded_len`, `encode_into`, `mip_dimensions`, `max_mip_count`, `DtexError`); crate `engine/tools_assetc` (library `pnm`, `mips`, `convert`, `cli` plus binary `assetc`).

```mermaid
flowchart LR
  SRC["source image: PPM P6 / PAM P7"] --> PNM["pnm::parse: RGBA8"]
  PNM --> MIP["mips::build_chain: 2x2 box filter"]
  MIP --> ENC["assets::dtex::encode_into"]
  ENC --> FILE[".dtex file: 20-byte header + mips"]
  FILE -. "bytes from the file system port" .-> RD["assets::dtex::Texture::parse (validates, no allocation)"]
  RD --> VIEW["Mip views: width, height, RGBA8 bytes"]
  VIEW -. "3-9/3-10 upload" .-> GPU["render device"]
```

`dtex` v0 header (little-endian): magic `DTEX`, version u16 (0), pixel format u8 (0 = RGBA8), flags u8 (bit 0 sRGB, others must be 0), width u32, height u32, mip count u32; then each mip tightly packed. Limits: 1 to 16384 per side, mips 1 to the full chain, file length must match exactly (shorter = `Truncated`, longer = `TrailingData`).

## Decisions and deviations

- **PNG is not read in this card.** Decoding PNG needs a third-party crate and its `THIRD_PARTY.md` T2 row, which is a governance edit (card text: "with a governance step"). The converter reads binary PPM (P6) and PAM (P7, RGB or RGBA, 8 bit), which need no dependency. PNG joins when the owner declares the governance step (a pinned crate in `tools_assetc` only, O5).
- `assets` has no dependencies (not even `base`): it needs only `core`. The file-system port supplies bytes to the caller, so the reader takes `&[u8]`.
- Mips are filtered on the stored values, also for sRGB textures (documented in `mips.rs`), with straight (non-premultiplied) alpha averaged like a colour channel. Levels are floor-sized, so for an odd source size **the last column or row is dropped** (a 5x3 image gives 2x1 from columns 0 to 3 and rows 0 to 1); clamping at the edge only matters for a 1-pixel side.
- A PAM `TUPLTYPE`, when present, must match the depth (`RGB` for 3, `RGB_ALPHA` for 4), otherwise `Unsupported`; an absent one is accepted. A CRLF after `maxval` is refused (`BadPixelData`), because the header ends after exactly one whitespace byte.
- The reader is heap-free; the encoder writes into a caller slice (`encoded_len` first). The tool allocates freely (dev-time).
- No governance file changed: `gates/architecture.toml` already maps `assets = 2` and `tools_* = 4`, and `assets -> platform/jobs` edges exist but are unused.
- The workspace `Cargo.toml` members list gained the two crates; `Cargo.lock` gained two entries.

## Independent review (read-only agent, run by the coordinator)

No blocker. Findings and what was done (fix loop 1 of 3):

- PAM `TUPLTYPE` was skipped, not checked against the depth: now validated (tests added, red first).
- `&bytes[HEADER_LEN..]` in the reader replaced by `bytes.get(..).ok_or(Truncated)`.
- Tests added: `Texture::mip` on a non-square odd chain with distinct per-mip bytes, a CRLF-after-maxval case, a numeric `box_down` test pinning the dropped odd column and row.
- Comment in `mips.rs` and this file now state the dropped odd edge and straight-alpha averaging on encoded values.
- **Deferred, not a defect of this card:** PNG input and its `THIRD_PARTY.md` T2 row wait for a governance step that the owner must declare.
- **As-built differs from wiki section 8** of `render-port-v0.md`: the header field order is magic, version, pixel format, flags, width, height, mip count (the page lists width and height before the format), and the flags byte holds the sRGB bit. The wiki is to be updated in a follow-up wiki card; this PR does not touch the wiki.

Before this, R1-R8 had been done as a self-review by the fork only (a fork cannot spawn agents).
