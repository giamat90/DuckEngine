# Roadmap Proposal `[P]`

Principle: **walking skeleton first, vertical slices after.** Always keep a runnable, tested, benchmarked engine; add depth only after the previous phase meets its exit criteria. Durations are intentionally absent: development is AI-driven and calendar time is not a constraint you care about (Q19), so phases are bounded by **exit criteria and review capacity**, not hours.

## Milestone reviews

At the end of each phase: metrics report vs previous (see [quality-metrics §4](quality-metrics.md)), ADR status, risk register update, and a go/adjust decision. Gates tighten (ratchet), never loosen without an ADR.

## Parallel tracks

- **Research track** (continuous): fill the gaps in [the survey](../01-state-of-the-art.md) before each relevant phase (audio before 5, render internals before 3, job system before 2).
- **Docs track**: ADRs accepted -> moved to `docs/adr/`; wiki pages updated at each milestone.

## Operating rules (Q2: solo, Q19: AI-driven, human = product owner / architect)

1. **Small WIP:** your review capacity, not typing speed, is the bottleneck. Keep at most 1-2 phase items in flight (several agents may work in parallel only on independent modules); finish tests + gates + docs before starting the next.
2. **Bound every phase by iterations and exit criteria, not hours.** If a phase needs more than about twice the planned agent iterations, or its exit criteria keep failing, stop and cut scope or stub with a stopgap adapter; do not extend silently.
3. **Early visible result:** the first demo (window + clear colour + triangle through the render port, using a stopgap GLFW/native window if needed) must appear by the end of phase 3, not later; momentum matters more when solo.
4. **Automation verifies the AI, you steer the architecture:** gates, arch checks, mutation-on-diff and an independent AI review replace line-by-line human review; human review is reserved for the change classes in [tdd-workflow §10](tdd-workflow.md).
5. **Wiki and ADRs are external memory:** every non-trivial decision is written down the day it is made, so a break of weeks does not lose context.
6. **Cut order when behind** (cheapest to drop first): second audio backend -> D3D12/Metal -> 3D phase scope (3D stays committed but is sequenced last, so it shrinks first) -> mutation testing on full runs -> ARM64 CI. Never cut: tests-first, arch checks, the null/headless adapters, benchmarks on hot paths.
7. **Phase-end review** (not calendar-based): metrics trend, **product review** (run the sample, check the product view in the metric report), design notes accepted, one-line keep / cut / change per open item.

## Scope-control rules

1. A new feature enters only if it serves the sample's exit criteria or a documented requirement.
2. "From scratch" items that block progress may use a **T1-stopgap adapter** with an exit plan (e.g. miniaudio) - the port keeps the door open. **Allowed (Q4, owner):** GLFW for the first window and input, miniaudio for the first audio output (SDL not used, owner preference); native Win32 and audio adapters replace them at a named milestone (target: before phase 7 closes), and each stopgap is removed from `THIRD_PARTY.md` when replaced.
3. Anything not in phases 0-7 is a backlog item, not a commitment.
